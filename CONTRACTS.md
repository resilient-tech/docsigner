# Protocol Contracts

Frozen interfaces between the 5 components. Change these only by editing this file first; every component builds against what's written here.

Protocol version: 1. All binary values are base64 strings unless stated otherwise.

---

## 1. REST API (signer-server)

Base path `/api`. JSON in, JSON out. Errors use HTTP 4xx/5xx with body:

```json
{ "error": { "code": "SESSION_EXPIRED", "message": "human readable" } }
```

Error codes: `DOCUMENT_INVALID`, `CERT_INVALID`, `SESSION_NOT_FOUND`, `SESSION_EXPIRED`, `SIGNATURE_INVALID`, `PROFILE_UNSUPPORTED`, `INTERNAL`.

### POST /api/signatures

Start a token-signing session.

Request:

```json
{
  "document": "<b64 PDF>",
  "certificate": "<b64 DER cert of the chosen signer>",
  "options": {
    "profile": "B-B | B-T | B-LT | B-LTA | CCA-LTV | CCA-LTA",
    "tsa": "optional registry name (digicert | sectigo | certum | entrust | ssl-com); absent = the server's TSA_URL. Arbitrary URLs are refused.",
    "digest_algorithm": "sha256 (default) | sha384 | sha512",
    "field_name": "Signature1 (optional, autogenerated if absent)",
    "reason": "optional",
    "location": "optional",
    "appearance": {
      "page": 0,
      "box": [72, 72, 272, 122],
      "position": "bottom-left | bottom-right | top-left | top-right (alternative to box)",
      "size": [200, 50],
      "text": "Signed by {signer}\n{ts} (optional, this is the default; {reason} is also substituted)",
      "image": "<b64 PNG, optional>",
      "style": "handwritten (optional; omit for the plain text stamp)",
      "name": "optional display name for the handwritten style; default = signer certificate CN",
      "capitalize": true,
      "bold": false,
      "qr_url": "optional URL; renders a QR panel at the stamp's right edge"
    }
  }
}
```

`appearance` absent = invisible signature. `box` is PDF points, `[x1, y1, x2, y2]`, origin bottom-left. Instead of `box`, a `position` corner preset may be given: the server computes the box from the actual page dimensions (24 pt margin), using `size` (width, height in points; default `[200, 50]`). When both are present, `box` wins.

`style: "handwritten"` draws the name in a bundled script font (Great Vibes) above the detail lines, ink-navy on transparent — a modern "wet signature" look with no image upload. `capitalize` (default true) uppercases each word's first letter; `bold` (default false) thickens the strokes. `qr_url` composes a full-height QR panel at the right edge of the stamp box and works with any style; `{signer}`/`{ts}`/`{reason}` substitution in `text` still applies. Both features render server-side into the stamp background; the plain text stamp without `qr_url` is unchanged.

Response 200:

```json
{
  "session_id": "<urlsafe random, 32 chars>",
  "to_sign_hash": "<b64, digest of the CMS signed attributes>",
  "digest_algorithm": "sha256",
  "expires_at": "2026-07-05T12:34:56Z",
  "pdfa": { "part": 2, "conformance": "B" },
  "pdfa_note": "present only for PDF/A input with a visible appearance"
}
```

`pdfa` appears only when the document claims PDF/A in its XMP. An invisible signature preserves PDF/A conformance; a visible stamp does not (unembedded font), which `pdfa_note` spells out.

### POST /api/signatures/{session_id}/complete

Request:

```json
{ "signature": "<b64 CMS-ready signature value>" }
```

Response 200:

```json
{
  "document_id": "<id>",
  "download_url": "/api/documents/<id>",
  "audit": {
    "signer": "CN=John Doe, O=...",
    "certificate_serial": "<decimal string>",
    "certificate_issuer": "CN=Some CA",
    "profile": "B-T",
    "digest_algorithm": "sha256",
    "field_name": "Signature1",
    "document_sha256": "<hex of the signed PDF>",
    "completed_at": "2026-07-07T12:00:00Z"
  }
}
```

`audit` is the machine-readable completion record (Zoho's "certificate of completion" analog); persist it alongside the document if you need an audit trail. `completed_at` is server wall time; the cryptographic time for timestamped profiles lives in the signature's RFC 3161 token.

Sessions are single-use and expire after 15 minutes.

For B-LT and B-LTA sessions the server embeds revocation data (DSS) and, for B-LTA, an archive timestamp before returning. The request and response shapes are unchanged; completion takes as long as the CA's OCSP/CRL endpoints take to answer.

CCA-LTV and CCA-LTA follow CCA India's application integration guidelines (ESAIG 1.19/1.25): a PKCS#7 signature whose chain and revocation data ride in the pdfRevocationInfoArchival signed attribute (OID 1.2.840.113583.1.1.8) rather than a DSS, with the signing time as a signed attribute. Revocation is fetched during `POST /api/signatures`, so that call takes the OCSP/CRL latency; CCA-LTA adds an RFC 3161 signature timestamp at completion. Both need TRUST_DIR; CCA-LTA also needs TSA_URL.

### POST /api/signatures/batch

Bulk signing: N PDFs, one token session, one PIN. The host's `signHash` already signs a batch of hashes with a single PIN prompt (section 2); these endpoints give the server side of that loop.

Request: `{ "documents": ["<b64 PDF>", "..."], "certificate": "<b64 DER>", "options": { same as POST /api/signatures, applied to every document } }`

Response 200:

```json
{
  "sessions": [ { "session_id": "<id>", "to_sign_hash": "<b64>" } ],
  "digest_algorithm": "sha256",
  "expires_at": "2026-07-05T12:34:56Z"
}
```

`sessions` is ordered like `documents`. Feed all `to_sign_hash` values to one `signHash` call, then:

### POST /api/signatures/batch-complete

Request: `{ "items": [ { "session_id": "<id>", "signature": "<b64>" } ] }`

Response 200: `{ "documents": [ { "document_id": "...", "download_url": "...", "audit": { ... } } ] }`, ordered like `items`.

Both batch calls fail fast: the first bad document or signature fails the request with its index named in the error message. Sessions completed before a mid-batch failure stay completed (their results are already stored), so complete a batch once. Batch size is capped at 50 documents.

### GET /api/documents/{document_id}

Returns the stored result. Media type by content: `application/pdf`, `application/xml`, or `application/pkcs7-signature` (detached CAdES). Documents expire after 1 hour.

### POST /api/sign-server-side

Signs with the server-held key (`.p12` from config). No session dance.

Request: `{ "document": "<b64 PDF>", "options": { same as above } }`
Response: `{ "document_id": "...", "download_url": "..." }` plus the `pdfa`/`pdfa_note` fields when applicable.

### CAdES: POST /api/cades/signatures, /api/cades/signatures/{id}/complete, /api/cades/sign-server-side

Detached CMS (.p7s) over any file, CAdES-BES. Same request and response shapes as the PDF endpoints, with two differences: `document` is any bytes (same size cap), and `options.profile` accepts only `B-B` or `B-T` (the CAdES archival ladder is not implemented). `appearance`/`field_name` do not apply.

### XAdES: POST /api/xades/sign-server-side

Enveloped XAdES-B over an XML document, signed with the server-held key. Request `{ "document": "<b64 XML>", "options": {} }`; response as sign-server-side. Token-based XAdES is not offered: XML-DSig assembly needs the private key in-process.

### POST /api/validate

Request: `{ "document": "<b64 PDF>" }`

Response:

```json
{
  "signatures": [
    {
      "field_name": "Signature1",
      "valid": true,
      "intact": true,
      "trusted": false,
      "modifications_ok": true,
      "signer": "CN=...",
      "signing_time": "2026-07-05T12:00:00Z",
      "profile_notes": "optional free text"
    }
  ],
  "pdfa": { "part": 2, "conformance": "B" }
}
```

`pdfa` is null when the document does not claim PDF/A.

`modifications_ok` reports whether every incremental update applied after this
signature is one PAdES permits (DSS, document timestamps, further signatures,
form fills). `false` means the document was altered after signing in a way a
reader should flag; `null` means the analysis could not run. `intact` only
covers the signed byte range, so a tampered document can still be
`intact: true` — check both.

## 2. Native messaging protocol (extension ↔ host)

Chrome native messaging framing (4-byte LE length prefix + UTF-8 JSON) on stdio. One request, one response, matched by `id`.

Request: `{ "id": "<string>", "command": "<name>", "params": { } }`
Success: `{ "id": "<same>", "result": { } }`
Error:   `{ "id": "<same>", "error": { "code": "<CODE>", "message": "..." } }`

Error codes: `USER_CANCELLED`, `PIN_INCORRECT`, `PIN_LOCKED`, `TOKEN_NOT_FOUND`, `CERT_NOT_FOUND`, `MODULE_ERROR`, `UNSUPPORTED`, `INTERNAL`.

### getVersion

Result: `{ "version": "0.1.0", "protocolVersion": 1 }`

### checkUpdate

Params: `{}`. The host compares its running version against a published one
fetched from `OPENSIGNER_UPDATE_URL` (a JSON feed `{ "version": "...", "url": "..." }`).
Version-check only — the host never downloads or installs. Network, HTTP, and
parse failures are soft: they return `updateAvailable: false` with an
explanatory `message`, never an error response.

Result:

```json
{
  "currentVersion": "0.1.0",
  "latestVersion": "0.2.0",
  "updateAvailable": true,
  "downloadUrl": "https://.../download",
  "message": "version 0.2.0 is available"
}
```

`latestVersion` and `downloadUrl` are null when no source is configured or the
check fails; `message` says which. When the source is unset, `message` is
`"no update source configured"`.

### listCertificates

Params: `{}` (host scans all configured PKCS#11 modules).

Result:

```json
{
  "certificates": [
    {
      "thumbprint": "<SHA-1 of DER, lowercase hex>",
      "certificate": "<b64 DER>",
      "subject": "CN=John Doe, O=...",
      "issuer": "CN=Some CA",
      "validFrom": "2025-01-01T00:00:00Z",
      "validTo": "2027-01-01T00:00:00Z",
      "keyType": "RSA | EC",
      "keyUsage": {
        "digitalSignature": true,
        "nonRepudiation": true,
        "keyEncipherment": false,
        "dataEncipherment": false,
        "keyAgreement": false,
        "keyCertSign": false,
        "crlSign": false
      },
      "tokenLabel": "ePass2003",
      "moduleName": "libcastle.so",
      "source": "pkcs11"
    }
  ]
}
```

`source` is `pkcs11` (found via a PKCS#11 module) or `os-store` (macOS Keychain / Windows certificate store). For `os-store` entries `moduleName` is `os-store` and `tokenLabel` is the store name (`keychain` on macOS, `MY` on Windows). A certificate visible through both paths is listed once, as `pkcs11`.

The result may also carry a `readers` array — connected smart-card readers seen by the OS smart-card service (PC/SC), which works even when no driver is installed:

```json
{
  "readers": [
    { "name": "Watchdata WDIND USB CCID Key 0",
      "token": "WatchData ProxKey",
      "driverFound": true }
  ]
}
```

`token` is the model guessed from the reader name (`null` if unrecognised); `driverFound` says whether a matching PKCS#11 module is installed. A reader entry with `driverFound: false` and an empty certificate list means: token plugged in, driver missing. The field is absent when the smart-card service is unavailable or no reader is connected.

### signHash

Params:

```json
{
  "thumbprint": "<hex>",
  "hashes": ["<b64 digest>", "..."],
  "digestAlgorithm": "sha256",
  "pin": "optional"
}
```

By default the host prompts for the PIN itself (native dialog) and all hashes in one call are signed within one PKCS#11 session: one PIN prompt for a batch. After a successful login the host caches the PIN in memory (per token label, 10 minutes), so further signHash calls on the same connection sign without re-prompting; the cache dies with the host process, which lives as long as the extension's native messaging port. A stale cached PIN (changed on the token) triggers one fresh prompt, never a blind retry. A page may instead supply `pin`, which the host uses directly with no dialog — the integrating page then owns PIN security (an XSS on that page can capture it) and gives up the per-signature consent dialog. An empty or absent `pin` means prompt as usual; a wrong one fails with `PIN_INCORRECT`. For `os-store` certificates the OS shows its own unlock/PIN dialog and `pin` is ignored; the wire shape is identical.

Result: `{ "signatures": ["<b64>", "..."] }`

Signature values are CMS-ready: PKCS#1 v1.5 block for RSA (host wraps digest in DigestInfo, mechanism `CKM_RSA_PKCS`), DER-encoded `ECDSA-Sig-Value` for EC (host converts the raw r||s from `CKM_ECDSA`).

On each successful signHash the host shows a best-effort desktop notification (macOS/Linux) naming the certificate, so a signing attempt is visible even when the PIN cache means no dialog appeared. It never blocks or fails the call. Set `OPENSIGNER_NO_NOTIFY` to disable it.

## 3. Page ↔ extension bridge (content script)

Page dispatches on `window`:

```js
window.dispatchEvent(new CustomEvent("org.opensigner.request", {
  detail: { requestId: "<string>", command: "<name>", params: {} }
}));
```

Content script replies on `window`:

```js
new CustomEvent("org.opensigner.response", {
  detail: { requestId: "<same>", result: {...} }   // or error: {code, message}
});
```

Commands are the native protocol commands plus `ping` (result `{ "installed": true, "version": "..." }`, answered by the extension without touching the host). Extra error codes at this layer: `EXTENSION_NOT_INSTALLED` (ping timeout, raised by signer-js), `HOST_NOT_INSTALLED`, `ORIGIN_DENIED` (user rejected the consent prompt).

First `listCertificates` or `signHash` from an unknown origin triggers the extension's consent prompt. The decision is remembered per origin.

## 4. signer-js public API

Single file, no dependencies, ES module + IIFE build. Global name `OpenSigner`.

```js
const signer = new OpenSigner();

await signer.init({ timeout: 2000 });       // rejects: EXTENSION_NOT_INSTALLED
const certs = await signer.listCertificates();  // array from §2, same fields
const { signatures } = await signer.signHash({
  thumbprint, hashes: [hash], digestAlgorithm: "sha256"
});
```

All rejections are `OpenSignerError` with `.code` from the codes above. Nothing else in the API. Server calls (start/complete) are plain `fetch` in application code; the demo shows the wiring.

## 5. Names

- Native messaging host name: `com.opensigner.host`
- Host binary name: `opensigner-host` (`.exe` on Windows)
- Page bridge events: `org.opensigner.request` / `org.opensigner.response`
- Extension IDs go into the host's native messaging manifests at install time; installers keep them in one place (a template variable), never hardcoded in code.

## 6. Shared conventions

- Digest algorithm default: `sha256`. Values allowed: `sha256`, `sha384`, `sha512`.
- Thumbprint: SHA-1 over the DER certificate, lowercase hex, no separators (matches what users see in Windows cert manager).
- Timestamps in JSON: ISO 8601 UTC.
- Component versions are independent; `protocolVersion` guards compatibility.
